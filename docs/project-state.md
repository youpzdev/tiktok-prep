# Состояние проекта

Локальный Python-сервер со стандартной библиотекой. Интерфейс на HTML, CSS и
JavaScript без сборки; обработка через ffmpeg и правку MP4-контейнера.
Запуск через start.bat или py -3 app.py.

Текущая задача: [SPEC.md](SPEC.md). Оформление: [design/design-main.md](design/design-main.md).
Решения: [decisions.md](decisions.md).

## Лендинг и рабочая область, 17.10.2026

Сайт написан заново. Лендинг и обработка используют чёрные поверхности,
молочный акцент и серебристый фон из broken-deepseek-mobile. Очередь, режимы,
настройки и результат доступны на одной странице. RU/EN и предпочтения
сохраняются. При перезагрузке вкладки восстанавливается активная задача;
если сервер больше не хранит её, очередь получает понятную ошибку с повтором.

Моушен: движущаяся подложка режимов, отклик загрузки на курсор, световой проход
кнопок, отклик нажатия, появление и удаление строк, движение прогресса и
раскрытие результата. Reduced motion отключает движение во время работы.
Шейдер и CSS-циклы приостанавливаются в скрытой вкладке.

Проверка tests/ui-check.cjs: 1440x900 и 390x844, очередь, режимы, RU/EN,
клавиатура, предпочтения, длинные имена, 12 файлов, ошибки, обработка и отмена.
Настоящие Stealth и Max проверяются через API на синтетическом видео.
Выбор путей, открытие проводника и часть ответов для ошибок/отмены подменены;
реальный системный диалог и проводник вручную не проверялись.

Проверка tests/ui-state.cjs: несколько отложенных загрузок не разблокируют
обработку раньше времени; потерянная задача не оставляет интерфейс заблокированным.
Оба сценария падали до исправления и прошли после него.
Потерянный ответ запуска сохраняет точный запрос и request_id до повтора,
включая reload. Сервер атомарно возвращает ту же задачу на повтор и отвергает
конфликт параметров. Восемь одновременных POST создают один worker. История
живёт в памяти сервера: смена instance_id снимает неопределённый pending
с предупреждением проверить результат, без автоматического нового запуска.
Прежний сервер распознаётся по отсутствию instance_id и требует перезапуска.

Проверка tests/ui-motion.cjs: hover, прерывание перехода режимов, очередь,
прогресс, результат, reduced motion. Запись: shots/workspace-motion.webm.
В замере 60 интервалов кадров с записью медиана около 16.7 мс.
При параллельных проверках p95 достиг 33.4 мс; в отдельном прогоне был 16.7 мс.
Это проверка локального headless Chromium, не измерение на реальном телефоне.

## Stealth и Max

Пользователь 17.10.2026 подтвердил рабочую публикацию Stealth с фиктивными
аудиосэмплами. Его алгоритм в этой задаче не менялся.

Max теперь всегда кодирует H.264 Main L5.2, slow, refs4, CRF14, 40M/80M;
штатные пределы 1080/1920/60, без апскейла. Контейнер, SEI и одна аудиодорожка
с фиктивными сэмплами следуют Stealth. Параметры кодировщика остаются
настраиваемыми через окружение. Max больше не поддерживает stream copy.

Python: 62 теста прошли. Новый профиль сначала дал 7 падений на старом коде.
Три мутации пойманы: возврат stream copy, старая маскировка, предел 120 FPS.
После восстановления повторён чистый прогон. Защита запросов также проверена
мутациями: отключение поиска прежнего запроса дало 7 падений, отключение
сравнения параметров дало 4 падения. Код восстановлен. Реальное 2048x1152@120 стало
1920x1080@60. Реальный process_job проверен с аудио и без него.
Реальные аудио- и видеопакеты до и после патча совпадают побайтово;
видео декодируется. Фиктивный AAC-хвост ожидаемо выдаёт ошибки декодирования,
реальный звук проверен отдельно. Качество публикации нового Max не проверено.
Существующий process_job выдаёт ResourceWarning о незакрытых pipe-объектах;
предупреждение не подавлялось, результаты кодирования проходят проверки.

## Telegram Stories: исследование и тестовые файлы

Пользователь публикует через AyuGram на Android, предположительно Vivo Neo 10, с Premium. Переносит ролик на телефон как файл. Версия AyuGram неизвестна. Предпросмотр выглядит нормально, опубликованная сторис заметно хуже.

Исходник Desktop/0926 (2).mp4: 1080x1920, 120 fps, 34.53 с, видеобитрейт 17.40 Мбит/с. Первый сохраненный экспорт: 720x1280, около 60 fps, 3.57 Мбит/с. После подготовки 1080p60 получен try1.mp4: 720x1280, ровно 60 fps, 3.53 Мбит/с. Битрейт посчитан по пакетам, служебные поля экспортов расходятся с ним.

try1.mp4 и try2.mp4 совпадают целиком: SHA256 97445F568B3EE28AFD390ACDD0F10F624F60E8113C5F4140CDE14ADCB21AC53E. Старый патч счетчика кадров не дал отличимого сохраненного результата. Повторное использование Telegram прежнего результата и сохранение той же сторис не различены.

Исследование от 27.09.2026:
- В официальном Telegram Android 12.10.5, commit dc780e81ed1261c369c27870e8e0999a1eb0b600, StoryEntry задает 720x1280 по умолчанию, ограничивает целевой битрейт обычного входного видео до 3 Мбит/с и частоту до 59. Реальный битрейт аппаратного кодировщика может отличаться. Это не точная идентификация установленного AyuGram.
- VideoEditedInfo.needConvert возвращает true для видеосторис из галереи. Хорошее превью не доказывает, что сжатие произошло на сервере: приложение может конвертировать при публикации.
- Ветка StoriesController без конвертации использует renameTo для исходника. Поэтому эксперимент сохраняет штатный конвертер, но пробует его ветку readAndWriteTracks без кодирования H.264.
- API сторис указывает максимум 30 МБ для видео. Premium описывает повышенное качество просмотра, а не обещание отправки исходного файла.
- Публичные исходники AyuGram4A/rewrite и exteraSquad/exteraGram/main устарели. Точная совместимость плагина с установленным клиентом требует проверки на телефоне.

Исходник плагина: [story_passthrough.plugin](../project/exteragram/story_passthrough.plugin). Это Python-плагин Story Copy Test 0.1.4 для API exteraGram 12.5.1+ / SDK 1.4.3.3+, без внешних зависимостей. Он проверяет точную сигнатуру фабрики ConvertVideoParams.of и обязательные поля. При несовместимости показывает Unavailable, не включает перехват.

Плагин проверяет реальные H.264/AAC-LC дорожки и отсутствие правок. После проверки меняет только needCompress=false и endTime=-1 в параметрах конвертера, чтобы копировать до конца файла. При ошибке записи возвращает прежние значения. Частота и порядок кадров проверяются по первым 121 временным меткам. Файлы для эксперимента подготовлены без B-кадров. Плагин не меняет VideoEditedInfo, не переносит исходник, не создает запросы публикации и не обращается в сеть.

Локальные проверки плагина: 33 теста проходят, включая полный callback, отказ по неподходящему видео, обычные сообщения, несовместимый интерфейс клиента, откат частичной записи, снятие перехвата и освобождение media-объектов. Тесты подменяют Java bridge и не подтверждают работу на Android. Настройки используют штатные строки клиента; глазами на телефоне не смотрел.

Версия 0.1.2 показывает этап отказа при загрузке, имя проверяемого поля, обнаруженные сигнатуры of при несовпадении и ограниченное сообщение исключения. Требования к интерфейсу конвертера сохранены. Пять проверок подробной диагностики падали на 0.1.1; после изменения все 41 тест проекта проходят. Для следующей проверки достаточно обновить и включить плагин, заново открыть настройки и прочитать статус; повторная публикация пока не нужна. Причина несовместимости с установленным клиентом еще не установлена. Новый текст настроек на устройстве глазами не смотрел.

На телефоне 0.1.2 сообщает Unavailable: method discovery; AttributeError: type. Остальная часть сообщения не видна в настройках. Это согласуется с возвратом Python-обертки Java-типа вместо объекта java.lang.Class; точный отсутствующий атрибут не прочитан. Описание find_class в текущей документации exteraGram не подтвердило поведение установленного SDK 1.4.3.3.

[Chaquopy Python API](https://chaquo.com/chaquopy/doc/current/python.html#classes) документирует вызов getClass на Python-обертке Java-типа как эквивалент ClassName.class. Нормализация должна сохранять прямой доступ для готового Class; getClass применяется только при отсутствии методов reflection, затем проверяется полное имя класса. Безусловный getClass недопустим: на готовом Class он возвращает java.lang.Class.

В 0.1.3 добавлена описанная нормализация класса. Тест с оберткой воспроизвел отказ на method discovery до изменения; после исправления проходят все 44 теста проекта. Проверены оба представления класса, однократное раскрытие обертки и отказ для другого имени класса. SDK и ограничения обработки не менялись. Исправление проверено на подмене Java bridge; реальная загрузка и копирование на телефоне пока не подтверждены.

Пользователь подтвердил, что 0.1.3 проходит method discovery и останавливается на signature check. Нормализация класса дала доступ к методам на устройстве. Сигнатура ожидаемого конвертера пока не совпала; найденные параметры не видны из-за обрезания строки настроек. Следующий шаг: получить полный отчет через штатное окно Diagnostics и Copy. Повторная публикация до успешной загрузки перехвата не нужна.

Проверен официальный [конвертер Telegram 12.5.1](https://github.com/DrKLO/Telegram/blob/ce8c61c47ec48a84014c8d1d0592f0e22a9dbb22/TMessagesProj/src/main/java/org/telegram/messenger/video/MediaCodecVideoConvertor.java#L1463). У фабрики of 18 параметров: отсутствует long videoOffset на позиции 2 относительно новой сигнатуры. VideoEditedInfo находится на позиции 17. Поле videoOffset отсутствует и в ConvertVideoParams, и в VideoEditedInfo; остальные используемые поля присутствуют. Ветка копирования AVC при needCompress=false сохранена. Это основание поддержать отдельный старый контракт; точная сигнатура установленного клиента пока не получена.

В 0.1.4 поддержаны только две проверенные сигнатуры: 18 и 19 параметров. Неизвестные типы и несколько подходящих фабрик отклоняются. Для старого контракта смещение нормализуется только в локальном словаре; поля Java не добавляются. Строгая проверка смещения для нового контракта сохранена.

В настройках добавлен пункт Diagnostics. Он открывает штатное окно с версией и полным сохраненным отчетом. Copy копирует именно показанный текст, Close закрывает окно. Тема и размеры элементов задаются клиентом. На устройстве окно глазами не смотрел; подключенного телефона для снимка нет.

Проверки 0.1.4: до изменения четыре проверки отсутствующего окна и старой сигнатуры не проходили. После изменения все 51 тест проекта проходят. Проверены полный callback старого конвертера, отказ по неизвестной сигнатуре, сохранение строгого нового контракта, показ отчета и точное копирование текста. Проверка текста: чисто. Следующая проверка на телефоне: обновить плагин и включить. При Ready можно повторить тестовый ролик; при Unavailable открыть Diagnostics, нажать Copy и передать отчет.
