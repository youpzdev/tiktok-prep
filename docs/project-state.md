# Состояние проекта

Локальный сервер Python со стандартной библиотекой. Веб-интерфейс: HTML, CSS, JavaScript без сборки. Запуск: start.bat или py -3 app.py. Обработка: ffmpeg и правка MP4 в mp4mask.py и mp4boxes.py.

Текущая задача: [SPEC.md](SPEC.md). Согласованное оформление: [design/design-main.md](design/design-main.md). Решения: [decisions.md](decisions.md).

Интерфейс реализован по согласованному макету. Снимки 1440x900 и 390x844 находятся в shots/ и просмотрены. Проверены пустая очередь, длинные имена, очередь из 12 файлов, клавиатура, переключение режимов и языка, сохранение настроек, раскрытие подробностей, удаление, очистка, ошибки и потеря соединения.

Проверка tests/ui-check.cjs запускается в Node с доступным Playwright. Переменные: TT_TEST_VIDEO указывает на короткое существующее видео, TT_TEST_URL задаёт адрес работающей утилиты, по умолчанию http://127.0.0.1:8766. Команда: node tests/ui-check.cjs. Проверка использует временные копии видео и убирает их после завершения.

Реальная обработка короткого файла через интерфейс завершилась с выходным MP4. Прогресс и отмена дополнительно проверены с контролируемыми ответами API. Выбор путей и загрузка файла в браузерных сценариях подменены; системный диалог и открытие проводника вручную не проверялись. Перетаскивание и передача тела файла проверены в браузере. Ошибок JavaScript нет.

Stealth: пользователь сообщил о 480p30 после публикации jotaro edit_tiktok.mp4. Локальный выход имеет 1080x1080, 60 fps, корректно декодируемые видео и основной звук. Фиктивная дорожка присутствует. Причина серверного пережатия не установлена.

Сравнены before-others-patch.mp4 и after-others-patch.mp4 с рабочего стола. По сообщению пользователя, первый опубликован в низком качестве, второй после дополнительной обработки конкурентом опубликован в высоком. Файлы не менялись.

Подтверждённые различия:
- До: H.264 High L4.2, 60 fps, 1172 кадра, 17.608 Мбит/с. После: Main L5.2, 59.357677 fps, 1170 кадров, 20.910 Мбит/с. Разрешение обоих 1080x1080. Видео и звук перекодированы.
- До: нормальный звук и отдельный раздутый клон. После: единственная аудиодорожка с 919 реальными и 8271 фиктивным сэмплом.
- После: mvhd version 1 с неизвестной длительностью; edts отсутствует; длительность mdhd аудио не включает фиктивные сэмплы, сумма stts включает.
- После: btrt сохранён, compressorname содержит Lavc libx264, у ключевых кадров есть SEI. Это опровергает необходимость удаления всех этих полей для каждого успешного файла.
- Оба файла содержат фиктивные данные после mdat. Само наличие такого хвоста не объясняет разницу публикации.

Stealth обновлён по образцу: Main L5.2, служебный SEI evc0 у ключевых кадров, сохранённые btrt, одна аудиодорожка с десятикратным числом сэмплов. Подробности текущего алгоритма находятся в README.md. Max сохраняет прежнее поведение.

Готовый файл: Desktop/tiktok_ready/before-others-patch_tiktok.mp4. Размер 49 085 021 байт, 1080x1080, около 59.357677 fps, 1172 видеокадра, 918 реальных и 8262 фиктивных аудиосэмпла. Это воспроизведение наблюдаемой структуры, а не побайтовая копия конкурента: у образца 1170 видеокадров и 919 реальных аудиосэмплов. Неизвестные настройки кодировщика не установлены по одной паре файлов.

Проверки:
- 18 тестов проходят. До реализации 6 тестов нового профиля падали. Два дополнительных теста реального кодирования воспроизвели ускорение VFR и потерю начального смещения видео; после исправления временных меток оба проходят.
- На итоговом ролике все 1172 видеопакета и 918 реальных аудиопакетов побайтово совпадают до и после изменения контейнера. Видео и реальный звук декодируются без ошибок. Ровно 14 служебных SEI совпадают с образцом.
- На 8262 фиктивных аудиопакетах декодер выдаёт ожидаемые ошибки. Полностью корректным AAC-потоком эту дорожку не называем.
- Проверены mvhd v1 с неизвестной длительностью, отсутствие edts, сохранение btrt, единственная аудиодорожка и хвост 66 096 байт за пределами mdat.
- Проверка интерфейса прошла на 1440x900 и 390x844, включая реальную обработку через API. Ошибок JavaScript нет. Снимки с новым описанием переключателя просмотрены.

Исходные метаданные очищаются. Случайное число и время из старого тега Max в новый Stealth не перенесены: его служебные поля повторяют образец. Уникальность файлов при повторном прогоне и распознавание ролика как нового контента платформой не гарантируются.

Качество публикации новым Stealth пока не проверено. Пользователь должен загрузить готовый файл для сравнения. Локальные проверки не устанавливают причину прежнего пережатия до 480p30.

## Telegram Stories: исследование и тестовые файлы

Пользователь публикует через AyuGram на Android, предположительно Vivo Neo 10, с Premium. Переносит ролик на телефон как файл. Версия AyuGram неизвестна. Предпросмотр выглядит нормально, опубликованная сторис заметно хуже.

Исходник Desktop/0926 (2).mp4: 1080x1920, 120 fps, 34.53 с, видеобитрейт 17.40 Мбит/с. Первый сохраненный экспорт: 720x1280, около 60 fps, 3.57 Мбит/с. После подготовки 1080p60 получен try1.mp4: 720x1280, ровно 60 fps, 3.53 Мбит/с. Битрейт посчитан по пакетам, служебные поля экспортов расходятся с ним.

try1.mp4 и try2.mp4 совпадают целиком: SHA256 97445F568B3EE28AFD390ACDD0F10F624F60E8113C5F4140CDE14ADCB21AC53E. Старый патч счетчика кадров не дал отличимого сохраненного результата. Повторное использование Telegram прежнего результата и сохранение той же сторис не различены.

Исследование от 27.09.2026:
- В официальном Telegram Android 12.10.5, commit dc780e81ed1261c369c27870e8e0999a1eb0b600, StoryEntry задает 720x1280 по умолчанию, ограничивает целевой битрейт обычного входного видео до 3 Мбит/с и частоту до 59. Реальный битрейт аппаратного кодировщика может отличаться. Это не точная идентификация установленного AyuGram.
- VideoEditedInfo.needConvert возвращает true для видеосторис из галереи. Хорошее превью не доказывает, что сжатие произошло на сервере: приложение может конвертировать при публикации.
- Ветка StoriesController без конвертации использует renameTo для исходника. Поэтому эксперимент сохраняет штатный конвертер, но пробует его ветку readAndWriteTracks без кодирования H.264.
- API сторис указывает максимум 30 МБ для видео. Premium описывает повышенное качество просмотра, а не обещание отправки исходного файла.
- Публичные исходники AyuGram4A/rewrite и exteraSquad/exteraGram/main устарели. Точная совместимость плагина с установленным клиентом требует проверки на телефоне.

Порядок проверки: установить story_passthrough.plugin в клиент с поддерживаемым API плагинов, включить и проверить статус Ready в настройках Story Copy Test. Сохранить storycopy_720p60.mp4 на телефоне с исходным именем. Создать видеосторис из галереи без изменений в редакторе. После публикации открыть настройки плагина заново: Copy requested подтверждает выбор ветки копирования, но не успешную публикацию и не сохранение качества сервером. Skipped и Unavailable означают, что обход не применен.

Сохранить опубликованный результат как try3_plugin60.mp4. Для чистого сравнения опубликовать тот же входной файл с отключенным плагином и сохранить как try3_control60.mp4. Затем при необходимости повторить с storycopy_720p30.mp4. Все копии переносить как файлы. Отключение или удаление плагина возвращает штатную обработку.

Исходник плагина: [story_passthrough.plugin](../project/exteragram/story_passthrough.plugin). Это Python-плагин Story Copy Test 0.1.1 для API exteraGram 12.5.1+ / SDK 1.4.3.3+, без внешних зависимостей. Он проверяет точную сигнатуру фабрики ConvertVideoParams.of и обязательные поля. При несовместимости показывает Unavailable, не включает перехват.

Плагин проверяет реальные H.264/AAC-LC дорожки и отсутствие правок. После проверки меняет только needCompress=false и endTime=-1 в параметрах конвертера, чтобы копировать до конца файла. При ошибке записи возвращает прежние значения. Частота и порядок кадров проверяются по первым 121 временным меткам. Файлы для эксперимента подготовлены без B-кадров. Плагин не меняет VideoEditedInfo, не переносит исходник, не создает запросы публикации и не обращается в сеть.

Локальные проверки плагина: 20 тестов проходят, включая полный callback, отказ по неподходящему видео, обычные сообщения, несовместимый интерфейс клиента, откат частичной записи, снятие перехвата и освобождение media-объектов. Тесты подменяют Java bridge и не подтверждают работу на Android. Настройки используют штатные строки клиента; глазами на телефоне не смотрел.

Итоговая локальная проверка: все 38 Python-тестов проекта проходят. Синтаксис плагина совместим с Python 3.11. Проверка текста с включенным расширением .plugin: чисто. Плагин скопирован в Desktop/TG_story_tests/story_passthrough.plugin; SHA256 совпадает с исходником.

Установка 0.1.0 на телефоне была заблокирована метаданными: установлен SDK 1.4.3.3, плагин требовал 1.4.4.3. В 0.1.1 нижняя граница SDK снижена до 1.4.3.3; проверка конкретного класса, полей и сигнатуры конвертера сохранена. Минимальный тест воспроизвел отказ до изменения метаданных. Это устранение блокировки установки, не подтверждение работы Java bridge на телефоне. Архив точной версии 1.4.3.3 в официальном репозитории сборок не найден.

В официальных [заглушках SDK 1.4.3.8](https://github.com/exteraSquad/plugins-pysdk-builds/releases/tag/sdk-v1.4.3.8-stable-25018973248-1) подтверждены используемые MethodHook, hook_method, unhook_method, log, find_class и Text. Это подтверждает отсутствие зависимости от новых API 1.4.4.3, но не заменяет проверку 1.4.3.3 на устройстве.
